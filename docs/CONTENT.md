# Corporator — контент как данные

Выход задачи T0. Задаёт **форму**, в которой живёт весь остальной контент: реестр типов, исполняемые схемы, генераторы, порядок композиции, правила линтера и политику версионирования пака.

Канон механик — `DESIGN.md`, визуальный дизайн HUD — `docs/reports/HUD_DESIGN_SYSTEM.md`, контракт экранов — `docs/SCREENS.md`. Этот документ не спорит с ними и не дублирует их: он говорит, как их содержимое превращается в данные, которые нельзя набить руками неправильно.

---

## 1. Принцип

Ни одна сущность игры не настраивается поэлементно. Есть схема, есть таблица параметров, есть генератор — конкретные сущности выводятся из них.

Из этого следуют четыре правила, и все четыре проверяются линтером, а не ревью:

1. **Выводимое не хранится.** Если значение выводится из другого значения — оно считается, а не лежит в файле. Одно и то же число в двух местах — дефект, а не удобство.
2. **Обоснование — это данные.** Параметр без ссылки на канон и без объяснения не проходит схему. Критерий приёмки «ни одного числа без обоснования» перестаёт быть пожеланием.
3. **Ручная правка — именованное исключение.** Каждое исключение занимает строку с причиной, и число исключений закупорено сверху. Подошли к потолку — значит правило описано неверно, и переписывать надо правило, а не расширять список.
4. **Пустое поле честнее выдуманного.** То, что ещё не посчитано, лежит в `pending` с указанием задачи-владельца и печатается линтером отдельным блоком. Ни один параметр не может потеряться между задачами.

### Что это даёт на практике

Матрица «кто сидит в каком здании» из `DESIGN.md` §5.8 — это 18 зданий × 5 ролей = **90 клеток, выписанных руками.** После T0 её нет в данных вообще. Вместо неё два поля у здания и одно у роли — **41 значение вместо 90**, и матрица собирается генератором.

Проверено механически: `content/build.py` собирает матрицу из контуров и сверяет её с дословной транскрипцией §5.8 в `content/fixtures/design_5_8.json` клетка за клеткой. Совпали все 90, **ручных исключений ноль.** Если правило когда-нибудь разойдётся с каноном хотя бы в одной клетке, сборка упадёт.

## 3. Что параметр, а что производное

Граница проходит по одному вопросу: **можно ли это вычислить из чего-то другого.** Если да — это не параметр.

### Экономика: девять чисел вместо девятнадцати

Канон §2.3 и §2.6 упоминает курсы 2000, 1960, 2200 и 2130, цену входа 2%, цену выхода ~9% и круг ≈15%. Из них параметров ровно четыре: потолок кассы и три ставки. 2000 — абсолютный потолок плавающего курса минта, не рабочий peg; трение считается вокруг курса и от него не зависит.

| Величина | Откуда | Значение |
|---|---|---|
| `capital_anchor` | параметр, §2.2–§2.3 | 2000 — потолок курса минта и множитель кассы |
| `vault_fee_bps` | параметр, §2.6 | 200 |
| `bank_markup_bps` | параметр, §2.6 | 1000 |
| `bank_markup_floor_bps` | параметр, §5.7 | 650 |
| курс минта в vault | **выводится** | 1960 |
| курс вывода через банк | **выводится** | 2200 |
| лучший курс с Trader | **выводится** | 2130 |
| цена выхода | **выводится** | 9.10% |
| цена выхода с Trader | **выводится** | 6.11% |
| полный круг | **выводится** | печатает `build.py` |
| круг с максимальным Trader | **выводится** | печатает `build.py` |

Ценность не в экономии символов. Ценность в том, что **нельзя поменять надбавку банка и забыть пересчитать круг** — линтер L13 проверяет, что круг остался в бюджете 14–16%, а L14 что вход всё ещё дешевле выхода. До T0 это была ответственность внимательности.

Границы бюджета сами лежат в `params/meta.json` с обоснованием, а не константами в коде линтера: `round_trip_floor_bps`, `round_trip_ceiling_bps` и `trader_round_trip_floor_bps`. Политику гейта тоже надо уметь прочитать и оспорить.

Побочный результат: выводя эти числа впервые, генератор сразу выдал расхождение R4 (см. §11) — круг с максимальным трейдером падает до 11.67%, то есть на 2.8 пункта ниже заявленного бюджета. Руками это никто не считал. Канон уточнён, скидка принята и ограничена снизу.

### Здания: 41 значение вместо 90

Контур — это ось «что делает слот». Роль объявляет, какие контуры для неё родные; здание объявляет свой контур и вторичный:

```
соответствие(роль, здание) =
    home       если building.contour           ∈ role.home_contours
    neighbour  если building.contour_secondary ∈ role.home_contours
    accepted   если building.accepts_any
    отказ IDLE_WRONG_ROLE иначе
```

Шесть контуров: `work_production`, `work_logistics`, `work_finance`, `work_retail`, `work_research`, `work_admin`.

Префикс `work_` не украшение. Без него `logistics` был бы одновременно районом и контуром, а `research` — контуром и задачей учёного, и строка лога перестала бы читаться однозначно. Идентификаторы в паке глобально уникальны, и это проверяет правило L03.

Trader — единственная роль с двумя родными контурами (`work_finance` и `work_retail`). Именно из этого сама собой получается головоломка §5.8: банк спит в воскресенье, магазин работает, поэтому трейдера на выходные пересаживают. Правило не знало про эту головоломку — она следствие.

Три здания не имеют родного контура: `city_hall`, `agent_hub`, `robotics_lab`. Все три помечены `autonomous`, и линтер L06 требует именно этого: здание, в котором никто не может работать, обязано работать без агента.

### Скоуп первой версии: одно поле вместо списка

`DESIGN.md` §11 перечисляет скоуп v1 прозой. Списка в данных нет. Есть правило: базовое здание играбельно всегда, маяк — по флагу `playable_v1` своего района, синергия — если играбельны все районы из её `requires`. Из шести играбельных районов получаются все **18 зданий**, и генератор сверяет их с дословной выпиской §11 в `content/fixtures/design_11_scope.json`.

Отсюда следствие, которое канон и получил (R6): `robotics_lab` открывается не по решению, а по правилу — оба её района играбельны. Снятие трёх оставшихся флагов тем же правилом открывает пять остальных синергий, без именованных исключений.

Резать скоуп теперь значит переключить один флаг района, а не править список в трёх местах. Правило L21 после этого проверяет ещё и обратную сторону: у каждого играбельного здания должна быть **объявленная** роль, которая может в нём работать, либо флаг автономности. Слот без роли в данных — ошибка сборки. Cloud Campus родной для Manager (G2); G1 открывает маяк вместе с Automation.

### Уровни зданий

Хранится точка нормировки на архетип и один показатель роста на всю игру. Стоимость, выход и время уровня N выводятся возведением в степень целочисленным `mulDiv`. Двенадцати строк «здание × уровень» в данных не будет никогда.

Параметры кривых закрыты в T2: `cost_growth_bps`, `output_growth_bps`, `energy_growth_bps`, `build_time_growth_bps` и точка нормировки. Три производных имени (`level_cost`, `level_output`, `level_build_time`) реализованы в `build.py` и входят в `IMPLEMENTED_DERIVED`. Широкая таблица 18 × 3 — `content/out/GENERATED.md`.

## 4. Композиция шаблонов

Порядок сборки фиксирован. Каждый шаг — чистая функция от результата предыдущих.

```
1. примитивы      палитра, рампы, единицы, коды, тексты
2. оси            контуры, ресурсы, показатели, ключи модификаторов
3. сущности       районы, архетипы зданий, роли, задачи, черты
4. правила        матрица соответствия, расписания, кривые уровней
5. мир            грамматика размещения → планировка → декор        (T10)
6. прогрессия     узлы = оси × районы × тиры; merge = дополнение синергий   (T4)
6b. модификаторы  caps из якорей, строки черт/задач/research/узлов, сплав     (T5, закрыт)
7. пак            каноническая сериализация + хеш
```

Ни один шаг не смотрит вперёд. Поэтому пак собирается за один проход и его сборка воспроизводима.

**Правило, которое надо держать:** новый контент — строка в таблице, трогающая один-два ключа модификатора. Фича, не выразимая так, в v1 не входит. Это не бюрократия: ключ уже умеет складываться, попадать в хеш, проходить линтер и отображаться в HUD, а новый механизм не умеет ничего из этого.

## 5. Детерминизм генерации и версионирование

### Каноническая форма

Пак — UTF-8 JSON с сортированными ключами и минимальными разделителями. Это ровно те байты, по которым берётся хеш, поэтому сборка на любой машине даёт один хеш. Текущий пак: **194**, **717 435 байт**, хеш `e8e837109fb0f34e3f125f86dd2195f60e491c86d5e24e2efb65d8aa39ff58fa` (`content/out/pack.sha256`). Причина 194: в CI `pnpm install --frozen-lockfile` вместо `pnpm -w install`, иначе ставятся только зависимости корня и `tsc` не видит `@corporator/*`. Ставки не менялись. Причина 193: CI ставит `requirements.txt` до `lint.py`, иначе пустой раннер падает на `jsonschema`; в `construction_tests` дописаны имена PL3 и PL6, которые L268 уже видел. Ставки не менялись. Причина 192: PL1, в `construction_tests` дописаны 64 имени vitest, которых L268 уже видел в тестах и не видел в дорожной карте (камера `island_client`, экран и публичный рейтинг `hud_screens`, байбек `buyback`). Ставки не менялись. Причина 191: публичный `GET /rating` без сессии, те же ряды, что живая доска. Ставки не менялись. Причина 190: снят поток `onboarding_demo` (экран, шесть `flow_onboard_*`, панель `onboard_stage`, поле `onboard_clock`, действия `onboard_next` и `onboard_wallet_offer`, `flows.onboarding_demo`, строка `UI_ONBOARDING`), инвентарь BRIEF T9 — 12 пунктов. Ставки не менялись. Причина 189: в `construction_tests` стадии `rpc_live` дописаны имена vitest приёмки вывода и порта, которых не было в дорожной карте. Тесты сайта в этот список не входят: `L268` их не сканирует. Ставки не менялись. Причина 188: кулдаун анстейка в сутках города, коды вывода до кошелька, кнопка `claim_unstaked`, страж L399. Причина 187: в `construction_tests` дописаны имена vitest, которых не было в дорожной карте, включая проход W25. Причина 186: в `oracle.stock_price` у строки тикера поле `stocks` — остаток `tokens_held`. Причина 185: словарь играбельности: постройка из карточки, анстейк, предъявление ваучера, коды сети. Причина 184: позывные совпадают с полом портрета. Женские имена только у Scientist и Logistician. Ключ `hN` и тик не менялись.

Плавающей точки в паке нет ни одной. Все ставки — целые в bps, загрузчик отвергает float-литерал на этапе разбора, а `assert_no_floats` перепроверяет собранный пак. Правило L10.

Хеш — sha256, а не keccak, и это осознанно: хеш пака — идентификатор во входе тика (`TickInputHeader`), не поле `DecisionRecord` (R-T11-3). Листья merkle остаются на keccak по §6.2. sha256 не тянет зависимость ни в один язык, на котором может быть написан публичный верификатор (§6.3).

### Зачем хеш во входе тика

Реплей смены (§6.3) пересчитывает тик из записанных входов. Если баланс с тех пор поменялся, пересчёт даст другой ответ, и запись будет выглядеть подделанной, хотя подделки нет. Поэтому `pack_hash` входит во вход тика, а опубликованный пак **не мутирует никогда**: правка даёт новый пак с новым хешем, старые записи продолжают ссылаться на прежний.

### Совместимость

| Изменение | Версия |
|---|---|
| добавлена сущность, которой не было | minor |
| изменён текст без изменения набора подстановок | minor |
| добавлен ключ, которого никто ещё не использует | minor |
| добавлено обоснование или ссылка на канон | minor |
| изменена формула генератора | **major** |
| изменён параметр, меняющий выход уже записанных смен | **major** |
| изменён порядок стадий применения модификаторов | **major** |
| удалён или переименован ключ, сущность или код | **major** |
| изменён набор подстановок у кода | **major** |

Порядок стадий применения модификаторов — в списке major именно поэтому. Он соответствует шагу 5 формулы §5.3 и после первой записанной смены не двигается.

Правило, которое ни разу не упало, ничего не гарантирует: одинаково выглядит и рабочий гейт, и опечатка в условии. Поэтому у линтера есть адверсариальная пара — `content/attack.py`.

Харнесс берёт контент, ломает его в памяти и требует, чтобы названное правило поймало поломку. Не поймало — падает сборка: виновато правило, а не атака. На шаге — `python content/attack.py --only` по затронутым id; полный `--jobs 8` — публикация пака и закрытие фазы (`R-C-4`). Конструкционные пробы (сейчас 296) входят только в полный прогон.

## 7. Исключения

Ручных исключений сейчас **ноль**, бюджет — шесть.

Это не формальность. До T0 казалось, что матрица §5.8 содержит особые случаи: `city_hall` пускает только управленца, `agent_hub` — только учёного соседом, `clearing_house` инвертирует контуры банка, `drone_depot` не пускает инженера, а `robotics_lab` вообще ни для кого не родной. Проверка показала, что все пять «особых случаев» — это обычные значения двух полей, и правило воспроизводит их само.

Вывод для всех последующих задач: **прежде чем заводить исключение, стоит проверить, не описана ли ось неверно.** Пять кажущихся исключений оказались одной пропущенной осью.

## 8. Арт по тем же правилам

`art/pipeline/` устроен правильно: `assets.json` декларативен, `tiles.py` держит таблицу id ромбов земли (`GROUND_KINDS`) и автотайл дороги/тротуара (`road_sprite` / `sidewalk_sprite`, `generated.render.road_autotile` / `sidewalk_autotile`; мелкая вода — `water_strip`). Конвейер пишет `art/out` (`pixelize`, `tiles`, `layout.py`); клиент архивного кадра читает `generated.placement.scene` из пака (`D-V-2`, `L184`, `L329`). `layout.py` сверяет `layout_hash`. Источник грамматики сетки — `params/placement.json` и `docs/archive/WORLD_PACK_GRID.md`. Авторский диорама `art/island_v3` — живой 3D-остров (`R-V-96`, `docs/archive/plans/PLAN_ISLAND.md`). Сетка `generated.placement.scene` остаётся экономической планировкой пака (`D-V-2`, `L184`, `L329`). Сетку пака на карту не переносить (`R-V-99`); квот жилья и «минимума зданий в районе» нет (`R-V-100`); юнитов нет (`R-V-101`).

Список недорисованного машинночитаем в `art/pipeline/assets_pending.json` (поля как у `assets.json`, плюс `status`, `silhouette`, `owner`). Линтер L16 по-прежнему помечает PENDING на `sprite: null`; L178 требует, чтобы у каждого здания и вида заполнителя был либо нарисованный спрайт, либо спека внутри лимита футпринта.

## 9. Тексты по тем же правилам

Один реестр по кодам: `params/codes.json` держит код, категорию и набор подстановок, `strings/ru.json` — текст. Тридцать три кода в трёх категориях: причина простоя, отказ на действие, состояние.

Текст, продублированный в коде клиента или сервера, — дефект. Правило L11 ловит код без текста и текст без кода, L12 сверяет подстановки в обе стороны: `{ticker}` в тексте, которого нет в слотах, и слот, который в тексте не используется, — обе ситуации ошибка.

Отсюда бесплатно получается локализация: второй язык — второй файл, а не поиск строк по коду.

Причина простоя обязательна по §5.3: `IDLE(нет energy)`, а не молчаливый ноль. Реестр делает это структурно невозможным нарушить — у статуса простоя нет способа не иметь причины.

## 11. Расхождения с каноном: решения

Найдено шесть, закрыты все шесть. Ни одно не осталось «на подумать»: два приняты как есть с обоснованием, четыре потребовали правки канона — она внесена в том же заходе.

**R1. §5.7 задаёт четыре уровня соответствия роли, §5.8 использует два.** Уровень 0.25 («чужое, но здание принимает») не назначен ни одному из 18 зданий.
*Решение: оставить как есть, канон не править.* Поле `accepts_any` со значением по умолчанию `false` стоит ноль, а удаление уровня меняет формулу тика — а изменение формулы делает непроверяемым реплей уже записанных смен (§6.3). Дешевле держать неиспользованный ноль, чем менять формулу после запуска.

**R2. §6.1 держит в записи поле `inputs.materials`, а §4.2 говорит, что расходуемых ресурсов ровно два.** Материалов как склада не существует.
*Решение: оставить поле, всегда ноль.* §6.4 требует канонического формата с первого дня именно для того, чтобы включение merkle-слоя не потребовало миграции истории. Убрать поле сейчас — значит поменять layout позже.

**R3. §4.2 называет вклад AMZN «Throughput — множитель», но §8 перечисляет пять показателей, и Throughput среди них нет.** Названо то, чего в модели нет.
*Решение: правка внесена.* Throughput — не показатель, а ключ модификатора `idle_reduction_bps`; так он и заведён в контенте. В §1 и §4.2 формулировка заменена на «режет простой по цепочке — множитель, не склад», в §5.8 — то же для Logistics Hub. Шестой показатель не заводится: пять — предел читаемости HUD.

**R4. Круг трения с максимальным трейдером — 11.67%, а не ≈15%.** Потолок 2130:1 из §5.7 вместе с составом 1/4/9/1 из §2.6 даёт вход 5.0% против выхода 7.0%. Инвариант «вход дешевле выхода» держится, принтера нет, но единственное число «≈15%» в §2.6 верно только для игрока без прокачанного трейдера.
*Решение: скидка принята, канон уточнён, граница снизу заведена в данные.* §2.6 теперь называет оба числа — 14.5% базово и 11.7% с максимальным трейдером — и объясняет, зачем существует потолок 2130:1. `bank_markup_floor_bps` не резался: это обесценило бы роль. Вместо этого появился параметр `trader_round_trip_floor_bps = 1100`, и правило L13 из предупреждения стало ошибкой в обе стороны — и когда скидка слишком велика, и когда её нет вовсе.

**R5. §10 говорит «токен $CORP с налогом на перевод», а §2.1 — что сбор живёт в свопе, а не в переводе.** §10 остался от первой редакции.
*Решение: правка внесена.* В §10 и §11 формулировка заменена на «со сбором создателя в пуле» со ссылкой на §2.1.

**R6. §11 вырезает из v1 все здания синергий, но `robotics_lab` требует NVDA + TSLA — оба района в v1 играбельны.**
*Решение: `robotics_lab` впущена в v1 единственной синергией, §11 переписан.* Решающий довод — не вкус, а бюджет исключений: правило «синергия играбельна, когда играбельны оба её района» открывает лабораторию само, и закрыть её можно было бы только именованным исключением. Первое исключение в системе ушло бы на то, чтобы отнять у игрока готовую фичу. Сверх этого: спрайт уже нарисован, автономный слот даёт v1 четвёртый тип фич («город работает без меня»), а без лаборатории пара NVDA + TSLA — та самая, которую открывают первой, — не имеет механического смысла. §11 теперь формулирует правило, а не список, и отсекает остальные пять синергий тем же правилом.

Расхождения по батчингу (§6.2 против батчера раз в минуту) и по сезонам (§12 против включения в скоуп) уже названы в `docs/archive/BRIEF.md` §2 и здесь не повторяются.

## 12. Как это запускать

```
python content/build.py      собрать пак в content/out/, сверить матрицу с §5.8, скоуп с §11 и кривую с KOTS
python content/lint.py       прогнать 373 правил, напечатать ошибки, предупреждения и ожидающие
python content/attack.py --only L13,L14   шаг: сломать затронутые правила и потребовать, чтобы гейт поймал
python content/attack.py --jobs 8         публикация пака / закрытие фазы: все правила и пробы конструкции
python content/builds.py     доминирование T4 → BUILDS.md / builds_summary.json
```

Порядок для правки контента на шаге: `build` → `lint` → `attack.py --only <затронутые L>`. Третий шаг не опциональный: он ловит случай, когда правило переписали и оно перестало срабатывать, а первые два шага при этом молчат. Полный `attack.py --jobs 8` — перед публикацией пака и на закрытии фазы, не на каждом шаге ТЗ.

Артефакты сборки в `content/out/`, руками не правятся:

| Файл | Что это |
|---|---|
| `pack.json` | канонический пак, те самые байты, по которым берётся хеш |
| `pack.sha256` | хеш пака, он же `pack_hash` заголовка тика (`TickInputHeader`), не поле записи |
| `GENERATED.md` | человекочитаемые сгенерированные таблицы: матрица соответствия, экономика, запуск, кривые T2, найм, XP, research, банк, возврат депозита, узлы T4 |
| `BUILDS.md` | счёт билдов и таблица доминирования T4 |

Зависимости: Python 3.10+ и `jsonschema`. Схема нарочно на JSON Schema, а не на инструменте одного языка: сервер и публичный верификатор (§6.3) должны сходиться в понимании валидности, не разделяя реализацию. Типы для TypeScript генерируются из той же схемы в T12.

`packages/engine` пак только читает. Сборщик и линтер в состав движка не входят, поэтому требование «тик без зависимостей» не нарушается. Каталога `packages/*` в дереве нет: границы заданы данными `params/arch.json`.
