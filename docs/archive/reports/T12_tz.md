## D1. Раскладка монорепо и закон слоёв

Три корня, а не один плоский `packages/*`: библиотеки, процессы и клиент живут разными жизнями, и смешивание их в одном каталоге стирает единственный дешёвый способ запретить зависимость.

```
packages/    engine, protocol, contentpack, chainport      — библиотеки, не имеют точки входа
services/    api, sampler, buyback, attestor, llm          — процессы, у каждого одна точка входа
apps/        client                                        — браузер
```

Слои нумеруются, зависимость разрешена **только вниз**:

| слой | пакет | что внутри | чем зависеть вправе |
|---:|---|---|---|
| `0` | `packages/engine` | чистая функция тика, записи, агрегаты, keccak, merkle | **ничем**, ни одной внешней зависимостью |
| `1` | `packages/protocol` | типы, коды, перечисления, конверт — **сгенерированы** из пака | ничем (только сгенерированные литералы) |
| `1` | `packages/contentpack` | загрузка пака по хешу, сверка `pack_hash`, отдача секций | `protocol` |
| `2` | `packages/chainport` | интерфейс `AssetPort` + `mock` + `rpc` | `protocol` |
| `3` | `services/*` | хост: расписание, БД, outbox, HTTP/WS | `engine`, `protocol`, `contentpack`, `chainport` |
| `4` | `apps/client` | сцена, HUD, экраны | `protocol`; `engine` — **только предпросмотр** |

Жёсткие запреты, каждый — правило линтера:

- `engine` не зависит ни от чего и не содержит I/O: список запретов уже написан в `docs/TICK.md` §2 и держится `L208`/`L209` на живом эталоне;
- ни один `services/*` не зависит от другого `services/*`. Общее живёт в `packages/*`, иначе граф сервисов превращается в скрытый монолит с циклом при первом рефакторинге;
- `apps/client` не видит `chainport`, БД и `services/*`. Импорт `engine` в клиенте помечен `preview_only = 1` и его результат **никогда** не пишется в состояние: `HUD.md` §8 «клиент не считает экономику»;
- `services/api` — единственный писатель в базу. Сэмплер, выкуп и аттестатор пишут в свои таблицы через тот же слой доступа, но ни один из них не двигает деньги игрока напрямую (`D9`, `D10`).

Граф объявляется таблицей в `content/params/arch.json` и проверяется на ацикличность топологической сортировкой в `content/arch.py`. Что ломается иначе: цикл `engine → server` убивает публичный верификатор `DESIGN.md` §6.3 — верификатор обязан импортировать движок без базы, RPC и HTTP.

## D2. Пак — единственный источник форм на проводе

Ни одно перечисление на проводе не набивается руками. `packages/protocol` — **сгенерированный** артефакт: коды из `codes.json`, капабилити и экраны из `screens.json`, ключи модификаторов из `modifier_keys.json`, районы и здания из своих секций, единицы из `$defs.unit`, номера версий из `meta.json`.

Таблица кодогена (`arch.json` секция `codegen`): `источник в паке → артефакт → потребитель → команда`. `api.json` и `arch.json` **ссылаются на ключи пака и не перечисляют значения**: перечисленное значение в двух местах — тот самый дефект «одно число в двух местах», только для строк.

Клиент получает пак **по хешу**: `GET /pack/{pack_hash}` отдаёт неизменяемый артефакт `content/out/pack.json` (`docs/CONTENT.md` §5: опубликованный пак не мутирует). Кеш — `immutable`. Старая смена находит свой пак по хешу из заголовка тика, не по «последнему» (`docs/TICK.md` §10).

## D3. Командная поверхность выводится из `screens.json`

Список мутирующих эндпоинтов **не проектируется**, он выводится: множество различных значений `effect` вида `commit:*` в `screens.json` `elements` даёт множество команд. Один `commit:X` — один `POST /command/X`. Биекция в обе стороны; ручной список путей в `api.json` запрещён.

Набор отказов эндпоинта тоже выводится: `requires` элемента → капабилити-токены → коды по матрице T9 (GENERATED «T9: элементы и отказы»), порядок — тотальный `(tier, token)` из `docs/SCREENS.md` §1 закон C. Блокирующий код на ответе один, остальные — в списке `hints`. Это тот же закон, что на кнопке, и второй его реализации быть не должно.

Элементы с `v1 = "stub"` (`missions_start`, `leaderboard_claim`) дают эндпоинт, который отвечает `FEATURE_NOT_IN_V1` и **ничего не меняет**: `spend = none`, ноль записей в money-таблицы. Отсутствие эндпоинта у заглушки хуже: клиент получит транспортную ошибку вместо честного кода.

## D4. Чтение: один снимок и никаких экранных эндпоинтов

`GET /city/{city_id}/state` отдаёт снимок, собранный **из `state_sources`** (`screens.json`, 17 строк): каждый источник — ровно одна секция снимка. Эндпоинтов «на экран» нет и быть не может: экран — забота клиента, сервер отдаёт состояние. Путь, в котором встречается `screen_id`, — дефект (правило).

Каждый ответ несёт конверт: `city_time`, `tick_index` (производный), `pack_hash`, `rules_version`. Клиент, у которого пак другой, обязан узнать это из конверта, а не из расхождения чисел.

## D5. Каналы WS и частоты из `HUD.md` §8

Пять классов частот, ровно как в каноне интерфейса, и ни одного шестого:

| канал | что несёт | когда |
|---|---|---|
| `tick` | Capital, Energy, Compute, статусы агентов, записи смены | по событию запечатанного тика |
| `log` | события | по событию |
| `aggregate` | GDP, Productivity, Happiness, Stability, Payroll | раз в тик, агрегатом |
| `price` | цены стоков и TWAP `$CORP` | по новому сэмплу сэмплера (D8) |
| `efficiency` | efficiency районов | на ветке `06:00` и при входе |

Часы города и плашка банка канала **не получают**: `HUD.md` §8 — «1 с, локально по формуле, без запроса». Канал для клиентских часов был бы 86400 сообщений в сутки за то, что клиент считает сам.

Каждый `state_source` попадает **ровно в один** канал и ровно в одну секцию снимка. Экономический источник имеет `source = server` — клиент не считает экономику (`docs/SCREENS.md` §1 закон E, `L158`).

## D6. Конверт ошибки: домен и транспорт — разные вещи

**Домен.** Отказ на действие игрока — HTTP `409` и тело `{code, slots, city_time}`. Текста на проводе нет: код плюс подстановки, текст рендерит клиент из `content/strings/ru.json`. Проза в ответе сервера — дефект того же класса, что текст, продублированный в коде (`docs/CONTENT.md` §8). Коды — только существующие: `NOT_ENOUGH_CAPITAL`, `BANK_CLOSED`, `STAKE_BELOW_THRESHOLD` и остальные из `codes.json`.

**Транспорт.** Отказ, которого в игре нет: клиент не туда постучал или сервис деградировал. Новая категория `transport` в `codes.json`, закрытый набор из шести кодов, каждый с текстом в `ru.json` (это держит существующее `L11`):

| код | HTTP | когда |
|---|---:|---|
| `API_MALFORMED` | `400` | тело не сходится со схемой команды |
| `API_UNAUTHORIZED` | `401` | нет сессии или подпись не сошлась |
| `API_RATE_LIMITED` | `429` | превышен лимит команд (D7) |
| `API_PACK_STALE` | `409` | `pack_hash` клиента не равен серверному |
| `API_INTENT_REPLAY` | `200` | повтор идемпотентной команды, отдан первый результат |
| `SERVICE_DEGRADED` | `200` | сэмплер или аттестатор за порогом лага (D13) |

Транспортный код **никогда** не попадает в `DecisionRecord.reason`, никогда не относится к категории `idle` и никогда не стоит в `requires` элемента экрана. Иначе транспорт протекает в экономику и реплей `DESIGN.md` §6.3 начинает зависеть от того, как игрок постучал.

## D7. Идемпотентность: команда без последствий при повторе

Каждая мутирующая команда несёт `intent_id` (уникален у клиента) и `expected_city_time`. Сервер хранит `(city_id, intent_id) → результат`. Повтор возвращает **первый** результат и `API_INTENT_REPLAY`, а не второй эффект. Без этого потерянный ответ на `commit:withdraw` — двойной вывод, а на `commit:build` — двойная трата.

`expected_city_time` устаревшая на больше, чем один тик, — отказ, а не «применим как получится»: игрок нажимал кнопку на другой картине мира.

Лимит команд не хранится, а выводится: `command_rate_limit_per_city_tick = 2 × agents_hard_cap` = `40`. Обоснование: физический смысл — одна команда на агента за час города плюс горстка городских действий; двойка — запас на переигрывание. Число в `api.json` не лежит.

## D8. Сэмплер: цена не объявляется, а проверяется

Сервис снимает TWAP пула `CORP/ETH` и фид `ETH/USD` по **фиксированным шагам** и пишет их в таблицу входов тика до того, как тик посчитан. Тик наружу не ходит никогда (`docs/TICK.md` §7, `L208`).

Период выводится, а не выбирается: `sampler_samples_per_tick = 75` (авторский) → `sampler_period_s = tick_length_real_seconds // sampler_samples_per_tick = 3750 // 75 = 50` с. Два условия, каждое — правило: период делит `tick_length_real_seconds` без остатка (иначе сэмплы уползают с фиксированных шагов `city_time`), и период `≤ 60` с (обещание `HUD.md` §8 «цены раз в минуту» нельзя выполнить каденцией реже минуты). Окно TWAP — существующий `twap_window_city_hours` = сутки города, то есть `24 × 75 = 1800` сэмплов в окне.

**Цена обязана быть перепроверяемой.** Заголовок тика несёт одно число `corp_eth_wei_per_whole`; верификатор, который умеет только сверить, что это число было использовано, не проверяет, что оно **правда**. Поэтому сырой ряд сэмплов публикуется: один глобальный объект в сутки (`price_day`), его CID ссылается каждый суточный агрегат города, дубля нет. Агрегация — одна функция `twap_from_samples(samples) = sum(samples) // len(samples)`, целочисленное среднее с полом, второй реализации нет; `rate_raw_from_samples` из тика её результат **потребляет**, а не пересчитывает. Это расширение `DESIGN.md` §6.2/§6.3 — `R-T12-3`.

Молчание источника: сэмплер пишет `feed_live = 0` и **последнее** значение с его настоящим возрастом. Обновлять метку времени у старого значения запрещено — это молчаливый ноль, только хуже: он выглядит свежим. Дальше работает уже описанная деградация вниз плюс `STALE_PRICE` (`economy.price_staleness_max_city_hours`, `price_stale_decay_bps_per_city_day`). Спот пула в путь минта не входит ни в каком виде.

Тик сэмплера не ждёт: нет свежего сэмпла — тик считает на последнем записанном и с кодом. Блокировка тика сэмплером ломает `DESIGN.md` §6.4 «выплата не ждёт записи» тем же способом, что блокировка аттестацией.

## D9. Конвейер выкупа: порядок, который держит кассу

Ни одного нового числа: каденция, транш, порог и запас уже посчитаны T1 и лежат в `launch.json` — `buyback_cadence_city_hours = 1`, `buyback_tranche_cap_bps = 33`, `buyback_min_batch_wei`, `buyback_slippage_safety = 3`. Сервис — транспорт, а не вторая калибровка. Транш считается от **живой** глубины, не от константы.

Порядок жёсткий и односторонний: `ETH со сборов → покупка $CORP → депозит в vault подтверждён → и только потом минт Capital в фонд`. Минт раньше подтверждения депозита — прямое нарушение инварианта кассы `DESIGN.md` §2.3 и I1/I3: в этот момент Capital существует без обеспечения. Правило и проба обязаны ловить именно перестановку.

Защита от фронтрана собственной покупки: факт выкупа предсказуем (фиксированный час города — так уже написано в `why` параметра), размер порции — нет. Порция режется потолком транша, отправка идёт приватным каналом провайдера, а при недоборе `buyback_min_batch_wei` сбор **копится** и в тик не входит. Никакой случайности «на глазок»: размер порции — функция от глубины и накопленного сбора, лог сохраняется.

Тик уже содержит `_buyback` над попавшим в казну ETH и меняться не должен — иначе поедет `A_t2`.

## D10. Аттестатор: падает открыто, лаг виден

Батчер минуты и суточный агрегат города — из `docs/TICK.md` §9, копий не делать. T12 добавляет только хост: outbox с ретраем, экспоненциальная отсрочка, метрика `attest_lag_ticks` (derived: запечатанные тики без корня), бейдж `· logged` вместо `Verified` до включения слоя.

Отказ IPFS, RPC или гейта не останавливает выплату, `raise` внутрь тика запрещён. Живая отправка корня в чейн остаётся `v1.1` (`DESIGN.md` §11, `R-T11-10` не закрывается этим шагом, а получает адрес сервиса).

Единственный контур, который падает **закрыто**, — сверка `pack_hash`: экономика на неизвестном паке не считается (`docs/TICK.md` §2, D9 шага T11). Таблица сервисов обязана нести колонку `fail_mode` со значением `open` у всех, кроме гейта пака.

## D11. Схема данных: канонические байты и ни одной производной как правды

Таблицы (состав — GENERATED, здесь смысл):

| таблица | ключ | смысл |
|---|---|---|
| `accounts` | `account_id` | `account_kind ∈ {demo, wallet}` — барьер BRIEF §2 |
| `cities` | `city_id` | anchor часов, уровень, `account_id` |
| `tick_inputs` | `city_id, city_time` | записанные входы, канонические байты + хеш |
| `records` | `city_id, city_time, agent_id` | `DecisionRecord` layout v1, канонические байты + хеш |
| `state_snapshots` | `city_id, city_time` | снимок состояния на границе суток |
| `outbox` | `id` | листья и корни, ждущие аттестации |
| `attest_roots` | `root_id` | корень минуты, состав, CID суточных агрегатов |
| `price_samples` | `sampled_at` | глобальный ряд сэмплов (D8) |
| `buyback_batches` | `batch_id` | сбор, транш, депозит, минт — четыре отметки времени |
| `vouchers` | `nonce` | ваучер банка: сумма, срок, одноразовость |
| `intents` | `city_id, intent_id` | идемпотентность (D7) |
| `fragments_ledger`, `seasons` | по канону T6/T7 | леджеры, а не пересчёт на чтении |

Законы схемы, каждый — правило:

- **байты, а не JSON-колонки.** Запись и заголовок хранятся ровно теми каноническими байтами, которые пошли в лист merkle, плюс их хеш. Пересборка JSON на чтении рано или поздно даст другой порядок ключей, и корень перестанет сходиться;
- **производное не хранится как правда.** `city_time` — правда, `tick_index` — вычисляемая колонка или индекс. Наоборот нельзя: `docs/TICK.md` §6;
- **каждое поле layout v1 и заголовка имеет дом в схеме.** Поле без дома — потеря входа для реплея §6.3;
- **снапшот выводится:** `state_snapshot_every_ticks = ticks_per_city_day` = `24`. Одна граница с суточным агрегатом IPFS и с закрытием GDP/Stability: три разных периода вместо одного — три разных способа не сойтись;
- **барьер демо.** `account_kind` стоит на каждой таблице, несущей деньги. Ни одного объявленного пути перевода `demo → wallet` и обратно. Демо-город изолирован, Capital не минтится, прогресс не переносится (BRIEF §2);
- **миграции только вперёд.** Опубликованный пак и записанные смены не мигрируют никогда.

## D12. Порт активов и роли ключей

`AssetPort` — интерфейс с двумя реализациями (`mock`, `rpc`) и ни одной третьей. Группы методов выводятся из `DESIGN.md` §10: токен `$CORP`, vault (депозит → минт, ваучер на вывод), реестр стейка стоков, реестр merkle-корней. Каждый пункт §10 «Ончейн» отображается ровно в одну группу; пункт без группы — дыра, группа без пункта — самодеятельность.

Импорт RPC-библиотеки разрешён **только** внутри `rpc`-реализации. Сервер знает интерфейс.

Ключи: `voucher_signer` (подпись ваучеров банка, `DESIGN.md` §10.1) и `buyback_executor` (отправка выкупа). Разделены: одна роль — один сервис, ни одна не живёт в клиенте, ни одна не используется вторым сервисом. Ваучер одноразовый по `nonce`, срок жизни выводится: `voucher_ttl_s = tick_length_real_seconds` = `3750` с, то есть один час города — ровно тот интервал, внутри которого дневной лимит, проверенный при выдаче, ещё не устарел.

## D13. Наблюдаемость: инвариант → метрика → порог

Правило, а не список дашбордов: **у каждого инварианта есть метрика, у каждой метрики — сервис-владелец, у каждого порога — источник.** Инварианты берутся там, где они уже названы: касса и I1/I3, бюджет трения `L13`/`L14`, пропорциональное урезание фонда, `I5`, `I7`, `I11`, детерминизм тика, `догон ≡ реплей`, байтовая стабильность layout v1, барьер демо.

Пороги: derived, если есть параметр-источник (`sampler_age_alert_city_hours = price_staleness_max_city_hours // 2` = `3` — алерт срабатывает **раньше**, чем устаревание начинает резать курс), иначе авторский параметр, чей `why` называет инвариант, который порог защищает, и отказ, который он предупреждает. Литерал порога в таблице метрик запрещён.

## D14. Деплой и готовность

Один процесс на сервис, окружения `dev` / `staging` / `prod`, миграции вперёд. Пак — контентно-адресуемый артефакт: образ пинит `pack_hash`, откат — это прежний образ с прежним хешем, а не «пересобрать пак».

`readiness` сервиса требует двух совпадений: `pack_hash` образа равен хешу загруженного пака и версия миграций равна ожидаемой. Сервис, готовый без пиннинга пака, — это сервис, который посчитает смену на чужом балансе.

## D17. `ROADMAP.md`: этапы с гейтом, а не с намерением

Каждый этап несёт: цель одной фразой, измеримый критерий готовности, **команду гейта**, которая его проверяет, и список идентификаторов инвариантных тестов. Этап без команды — намерение. Каждый инвариант из D13 обязан появиться минимум в одном этапе — иначе он не проверяется нигде.
