# Финальное ревью перед запуском Corporator

Дата проверки: 2026-10-01. Вердикт ниже относится к **рабочей копии**, не к коммиту `HEAD`.

## 1. Вердикт: NO-GO

Запуск токена и деплой контрактов **не** делают игру полностью играбельной и **не** закрывают уже подтверждённые дыры.

Денежный путь и процесс запуска нельзя считать готовыми:

- API при неполном RPC-окружении молча берёт мок-кастоди, и флаг `CORPORATOR_DEPOSITS_OPEN` этот выбор не запирает.
- Повтор минта Capital на чейн коммитится в БД как «долга больше нет» **до** отправки `mintCapital`. Падение процесса между этими шагами оставляет игровой Capital без повторной попытки.
- Неаутентифицированное создание demo-города держит единственный мировой лок. Тик обходит все города. Потолка числа городов нет.
- Собственный гейт `python content/lint.py` на этой копии красный: 3 ошибки, exit code 1.
- HUD не дописывает вывод и не забирает созревший анстейк: Present уходит без `voucher_id`, Claim unstaked на цепочечном пути — без `district_id`.
- Самплер пишет цены в память процесса. Тик читает `price_samples` из Postgres и при пустой таблице считает фид живым. Доля фонда с оборота в Vault не отправляется. Депозит котла идёт через `eth_sendTransaction`, не ключом исполнителя. API зовёт байбек по адресу собственного `CORPORATOR_LISTEN_BIND`.
- `forge` и `docker` на машине проверки отсутствуют. Контрактные тесты Foundry и сборка прод-образа **не выполнены**. Это не доказательство дефекта контракта и не доказательство готовности.

Внешний аудит подрядчиком не заменяет этот документ. В `docs/AUDIT.md` владелец принял, что ожидание подрядчика не блокирует P4. Для подписи `launchToken` это остаётся отдельным решением владельца, не закрытым кодом.

Подтверждённых P0 (прямая кража или несанкционированный минт, воспроизведённые исполнением) в этой проверке нет. P1 достаточно для NO-GO.

## 3. Станет ли игра полностью играбельной после токена и деплоя контрактов

Нет.

Канон (`docs/LAUNCH.md`, `docs/CANON.md` R-W-05, D-P-14) уже говорит, что между `launchToken` и первым депозитом нужны четыре деплоя наших контрактов, адреса в env, сверка `creatorTaxBps() = 200` и снятие режима «депозиты закрыты». Graduation и сид пула для первой покупки на кривой не требуются: игрок покупает на кривой. Это необходимый список, но по коду его недостаточно.

Что ещё обязано случиться, и чего «токен существует» не заменяет:

1. Заполнить `content/params/launch.json` → `deployed` (пять полей). Пока любое пустое, клиент и `prepareClaimPrize` держат `claim_prize` в отказе (`DEMO_NO_PRIZE` / `refusal-only`). Адреса казны в env **не** включают кнопку. Это смена пака: новый hash, `codegen`, `PACK_HASH` у процессов. Утверждение «адрес меняется без пересборки» верно для `CORPORATOR_VAULT` и соседних env (`readPlayerReady`), и неверно для включения приза.
2. Задать RPC, chain id, timeout, пять адресов контрактов, ключи ролей `minter` / `voucher` / `signer` / depositor байбека, `CORPORATOR_HOP_URL`, фид ETH/USD, стоковые адреса `CORPORATOR_STOCK_*`, IPFS для аттестатора. Нет полного RPC — API остаётся на моке (F-01).
3. Поднять Postgres, прогнать миграции, поднять api, sampler, buyback, attestor. Образ `corporator:${PACK_HASH}` описан в `docs/OPS.md`. На этой машине образ не собирался: Docker нет.
4. Самплер при `CORPORATOR_DEPOSITS_OPEN=1` без RPC и фида завершается с кодом 1 (`services/sampler/src/source.ts`, `main.ts`). Это сделано. API тот же флаг не читает.
5. Пустые котлы Farm/месяца до первого swap с логом `Transfer` на `buyback_executor` — ожидаемое состояние (R-B-06), не повод минтить сток. Призы в первый час пустые.

## 4. Находки

### F-01 — API молча остаётся на моке, флаг открытия депозитов его не закрывает

- Уровень: **P1**. Статус: **подтверждённый дефект** (ветка кода однозначна; процесс с этим env в этом проходе не поднимался).
- Где: `services/api/src/custody.ts` `selectApiPort` / `liveRpcConfig` (строки 31–62); `services/api/src/main.ts` `startMain` (строки 35–40); `packages/chainport/src/rpc/playerReady.ts` `depositsOpen` (строка 39).
- Требование: R-W-05 и `docs/reports/TZ_PLAYABLE.md` — при `CORPORATOR_DEPOSITS_OPEN=1` без сети процесс не стартует и не кормит игру сидом. Самплер это делает (`services/sampler/src/source.ts` строки 12–18, `main.ts` строки 30–33). API — нет.
- Как возникает: в env API выставлен `CORPORATOR_DEPOSITS_OPEN=1`, но нет одного из `CORPORATOR_RPC_URL`, `CORPORATOR_CHAIN_ID`, `CORPORATOR_RPC_TIMEOUT_MS` или любого из пяти адресов. `liveRpcConfig` возвращает `undefined`, `selectApiPort` вызывает `createMockPort`. `prizeCustodyLive` ложен. `liveStartRefusal` при `live=false` возвращает пустую строку даже при грязном леджере.
- Факт: пустой env в тесте `services/api/test/h2.test.ts` (`mock_port_is_not_prize_custody`, около строки 2181) обязан давать `kind === "mock"`. Поиск `depositsOpen` по `*.ts` находит только объявление и тест `packages/chainport/test/l8.test.ts`. Игровые команды поле не читают.
- Обратная сторона: полный набор адресов и RPC включает живой порт **без** флага. Флаг не является рубильником банка.
- Последствие: оператор считает депозиты открытыми, игроки минтят Capital из `corp_held` мока. Вывод на моке увеличивает `corp_held`, ваучер Vault не выпускается. Позже включённый RPC упирается в `LEDGER_NOT_EMPTY_LIVE` и процесс не стартует. Игровой Capital не обеспечен депозитом в Vault.
- Исправление: если флаг равен `1`, а `liveRpcConfig` пуст — `startMain` завершается с ненулевым кодом, как самплер. Не выбирать мок. Приёмка: тест, в котором флаг `1` и нет `CORPORATOR_VAULT`, процесс не слушает порт; тест, в котором адреса есть и флаг не `1`, фиксирует выбранное владельцем поведение (живой порт или отказ) явно.

### F-02 — долг минта Capital списывается в БД до отправки транзакции

- Уровень: **P1**. Статус: **подтверждённый дефект** (порядок коммита читается прямо; SIGKILL в этом проходе не ставился).
- Где: `services/api/src/commands.ts` `settleServerMint`, строки 83–105, повтор при неудаче — строки 107–123.
- Требование: запись состояния и сеть не должны расходиться так, чтобы повтор стал невозможен. Рецепт лока: сеть не внутри транзакции БД; истина минта — чейн (R-X-06 для ваучера; для минта тот же риск).
- Как возникает: под мировым локом `chain_mint_capital` обнуляется и `COMMIT` проходит. Затем, уже вне этой транзакции, вызывается `mintCapitalOnce`. Если процесс убит после коммита и до успешного ответа, долг не возвращается. Ветка `if (!posted) восстановить долг` при смерти процесса не исполняется.
- Если `mintCapital` на чейне уже прошёл, а ответ потерян, повтор безопасен только пока `pending[account] > 0`. Иначе смотри F-05: повтор упирается в `require(queued > 0)` и долг остаётся навсегда, хотя Capital в игре уже начислен.
- Последствие: игрок имеет Capital в снимке. `$CORP` может остаться в `pending` Vault и не войти в `backingOf`. `voucherRoom` вычитает `totalPending`, выход ваучером этой суммы не покрывает. Игрок застревает без пути, который код сам догонит.
- Исправление: не коммитить обнуление долга до известного успеха `mintCapital` **или** хранить неотправленный долг в той же строке, которую сверщик поднимает после рестарта, и считать успехом уже существующий `capitalOf` / событие, а не только ответ RPC. Приёмка: тест, который обрывает процесс после `COMMIT` обнуления и до `mintCapital` и показывает, что следующий старт снова минтит ровно недостающее и не минтит второй раз.

### F-03 — demo-сессия без подписи держит мировой лок и плодит города

- Уровень: **P1**. Статус: **подтверждённый дефект**.
- Где: `services/api/src/session.ts` `authSession` при `account_kind === "demo"` (строка 160) → `issueDemoSessionMut` (строки 201–232); `services/api/src/city_lock.ts` строки 6–8 и 46–61; тик обходит `sortedKeys(cities)` в `packages/engine/src/tick.ts` (например строки 64–70). Лимит команд `incrementCommandRate` есть только на командах города, не на `/auth`.
- Требование: публичная точка входа не должна давать одному клиенту остановить команды всех игроков и раздувать состояние тика.
- Как возникает: `POST` сессии с `account_kind: "demo"` не требует адреса и подписи. Каждый новый id города пишется под `withWorldLock`. Комментарий лока: одна очередь на весь мир, тик, команда и логин делят её. Поиска `max_cities` / потолка demo в рантайме нет (`fragment_city_cap_bps` — это доля фрагментов, не число городов).
- Длина тика: `tickLengthRealMs = 3750000` (`packages/protocol/src/listen.ts`), около 62.5 минут. Граница «сколько городов укладываются в этот интервал» **не измерялась**.
- Последствие: поток demo-логинов сериализует все команды и тик. Города остаются в состоянии навсегда и входят в каждый тик.
- Исправление: лимит новых demo на адрес/ключ/окно, отказ при переполнении, и не держать мировой лок дольше записи одной строки. Приёмка: N параллельных demo-auth не блокируют команду уже существующего города дольше заданного бюджета; после отказа сверх лимита число городов не растёт.

### F-05 — `mintCapital` забирает весь `pending` счёта

- Уровень: **P2**. Статус: **подтверждённый дефект контракта**; двойной депозит в этом проходе на чейне не исполнялся (Foundry нет).
- Где: `contracts/src/Vault.sol` `mintCapital`, строки 107–117: `pending[account] = 0` и в `backingOf` уходит весь `queued`, а `capitalOf` растёт только на переданный `capitalAmount`.
- Как возникает: два `deposit` одного аккаунта уже в `pending`, первый `mintCapital` вызывается на Capital только первого депозита. Второй `mintCapital` получает `pending == 0` и откатывается. `$CORP` обоих депозитов уже в `backingOf`. Игровой учёт может начислить Capital за оба (`commitDepositMint`), а `chain_mint_capital` второго зависает (F-02).
- Последствие: `capitalOf` на чейне меньше игрового Capital. Ваучер смотрит на backing и баланс токена, не на `capitalOf`, поэтому это не само по себе выдача чужих `$CORP`. Это порча зеркала и вечный ретрай минта.
- Исправление: минтить и переносить в backing только ту часть `pending`, которая соответствует этому вызову, остаток оставлять в `pending`. Приёмка: два депозита, два `mintCapital`, оба `capitalOf` сложились, остаток `pending` нулевой только после второго.

### F-08 — депозит подтверждается одним receipt без глубины

- Уровень: **P2**. Статус: **вероятный риск**. Реорг на Robinhood Chain в этом проходе не измерялся.
- Где: `services/api/src/commit_bank.ts` `verifyDepositConfirm`, строки 1208–1216: `transactionReceipt` со `status === 1n` и сверка `from` / `to` / `input` с рецептом. Числа подтверждений нет. В `packages/chainport/src/rpc/live.ts` receipt читается через `eth_getTransactionReceipt`.
- Что сделано правильно: сумма сидит в calldata рецепта, чужой `from` отвергается, повтор того же hash режется ключом `chainTxKey`.
- Последствие: receipt, который потом исчезнет из канонической цепи, уже мог начислить Capital и `vault_corp` в БД.
- Исправление: параметр пака «сколько подтверждений» и сверка, что tx всё ещё в канонической цепи. Приёмка: фикстура reorg, в которой первый receipt успешен, а второй чтение его не видит, и Capital не остаётся начисленным.

### F-09 — CORS отражает любой Origin

- Уровень: **P3**. Статус: **подтверждённый дефект ограниченного сценария**.
- Где: `services/api/src/listen.ts` `securityHeaders`, строки 44–53. `Access-Control-Allow-Credentials` не ставится. Сессия — bearer, не cookie.

- Исправление: список origin из env. Приёмка: чужой `Origin` не получает `Access-Control-Allow-Origin`.

### F-10 — тест депозита H2.9 флакает о бюджет 60 с

- Уровень: **P3**. Статус: **подтверждённый дефект теста**, не дедлок депозита.

### F-15 — депозит котла не подписывается ключом исполнителя, филл при этом списывается

- Уровень: **P1**. Статус: **подтверждённый дефект проводки**. Повторный своп на живом хопе не исполнялся.
- Где: swap подписывается raw-транзакцией. `prizeDeposit` и `putRoot` идут в `sendTx` (`packages/chainport/src/rpc/live.ts` строки 184–191, 447–457, 429–433): метод `eth_sendTransaction`. `keptCarry` (`conveyor.ts` строки 111–114) не возвращает `sendWei` в остаток, если филл уже `> 0`, даже когда `depositHop` не удался. `createConveyorSubmit` всё равно пишет `state = out.next` (worker.ts строка 185). ### F-19 — два процесса API пишут одну строку мира разными локами

### F-21 — простой процесса не сдвигает часы города на прошедшую стену

- Уровень: **P2**. Статус: **подтверждённое поведение**. Это не принтер. Проход нагрузки назвал его P1. Часы города в этом репозитории — часы писателя тика, не `Date` внутри тика. Догон стены при старте сменил бы модель. Оставляю P2 как операционный сюрприз, не как дыру кассы.
- Где: `main.ts` строки 49–56: `lastMs = Date.now()` при старте, первый `due` обычно 1 после интервала 3 750 000 мс.
- Последствие: часы и сутки простоя не превращаются в пачку тиков. Банк и зарплата стоят, пока процесс лежит, и не догоняют календарь после подъёма.
- Что решить владельцу: пауза города на простое — норма, или старт должен догнать не больше `offline_hard_cap`.

### F-22 — ваучер может опереться на backing дома, пока депозит ещё в `pending`

- Уровень: **P1**. Статус: **вероятный риск**. Проход контрактов назвал это P0. Повторяю формулу, не исполнение. На пустом доме при запуске комнаты нет, кражи нет. Риск включается, когда у дома уже есть backing, а `mintCapital` ещё не перенёс `pending` игрока.
- Где: `Vault.voucherRoom` (строки 133–141) вычитает `totalPending` и чужой backing, но оставляет избыток дома. `presentVoucher` при нулевом своём backing берёт дом (строки 152–160). Игровой Capital пишется в `executeDepositConfirm` до квитанции `mintCapital` (F-02).
- Последствие: один депозит может дать выход из дома и второй выход после того, как тот же `$CORP` станет `backingOf` игрока.
- Исправление: не выпускать ваучер, пока `mintCapital` этого депозита не виден в квитанции и `pending` игрока не обнулён этим минтом. Приёмка: дом с backing, депозит в `pending`, `withdraw` до минта не уменьшает `backingOf(house)`.

### F-23 — золотые векторы тика на старом hash пака

- Уровень: **P3**. Статус: **подтверждённый дефект свидетеля**. Прогон [Движок и экономика](6ab6392d-3954-463c-96a1-407d235ac916): `npx vitest run packages/engine/test/c1.test.ts`, `layout_v1_bytes` красный. Формулу тика из-за красного заголовка не менять.
- Отдельно, на этом паке не стреляет: `content/build.py` делит храповик как `elapsed // 24`, TypeScript — на `ticks_day`. Сейчас оба видят 24. Если `ticks_day` уйдёт от 24, двойники разъедутся. Это P2 латентный, не текущий принтер.

### Что из чужих P0 не стало P0 здесь

Проходы деплоя, байбека, chainport и канона ставили P0 на мок-депозит, обрыв самплера, `eth_sendTransaction` котла и невызванный `depositThenMint`. ## 10. Чеклист запуска, когда NO-GO снят

Необратимое on-chain не откатывается деплоем предыдущего образа. Откат сервера — предыдущий образ со своим `PACK_HASH` (`docs/OPS.md`). Уже выпушенный ваучер и уже переведённый `$CORP` образ не возвращает.

1. До подписи: внешнее решение владельца по аудиту; `lint` зелёный; Foundry зелёный; hash пака совпадает с тем, что уйдёт в образ; `launch.deployed` всё ещё пуст; `creator_tax_bps` пака равен 200.
2. `launchToken` без `launchAndBuy` (`launch_buy_share_bps = 0`). Записать tx. Сверить `creatorTaxBps()` кривой с 200. Не открывать депозиты в ту же минуту, пока сверка не записана.
3. Деплой Vault, StakeRegistry, PrizeTreasury, MerkleRoots скриптом `contracts/script/PlayerReady.s.sol` из env. Роли: minter, voucher signer, prize signer, depositor байбека. Паузы нет — ошибки ролей лечатся только новым деплоем, если конструктор это позволяет, либо принятием контракта как есть.
4. Адреса в env хоста. Отдельный шаг: вписать пять полей `launch.deployed`, поднять `pack_version` по `docs/CONTENT.md` §5, собрать пак, прошить новый `PACK_HASH`. Без этого призы остаются отказом. Это нормально до заполнения, и это не «само включится от env».
5. Миграции на пустой БД. `/ready` зелёный только при том же hash и версии миграции.
6. Порядок процессов: Postgres → migrate → api, sampler, buyback, attestor. У api полный RPC, иначе он не должен стартовать (после F-01). У самплера фид. У байбека hop URL, иначе котлы остаются на моке и это видно по отсутствию депозитов, а не по тихой выдаче стока.
7. `CORPORATOR_DEPOSITS_OPEN=1` только когда шаги 2–6 зелёные. Первый игрок: покупка на кривой, approve, deposit, confirm, Capital в снимке, постройка списывает Capital, вывод даёт ваучер, present приносит `$CORP` в кошелёк. `corp_held` и `tokens_held` кошелькового города остаются 0.
8. Первые часы: самплер живой, `mint_rate` не ноль, ваучеры в `SIGNING` не старше TTL без сверщика, котёл пуст и призы не обещают выплату, лаг аттестации не блокирует тик, Postgres не торчит наружу, лог без `LEDGER_NOT_EMPTY_LIVE`.
