## 1. Диагноз: почему сейчас $3 в день

Все числа ниже сняты с пака 176 при `capital_unit_usd = 100`, то есть **1 Capital = $0.000001**. Воспроизводятся `python content/build.py`.

### 1.1 Что игрок получает сегодня

| архетип | tier | output | цена L1 | выход за тик | выход за сутки города | окупаемость |
|---|---|---|---|---|---|---|
| `workshop` | base | capital | $34.22 | $0.1426 | $3.4218 | 240 тиков |
| `robotics_lab` | synergy | capital | $136.87 | $0.3422 | $8.2123 | 400 тиков |
| `flagship_store` | beacon | capital_from_population | $85.54 | 0 | 0 | — |
| `retail_complex` | synergy | capital_from_population | $136.87 | 0 | 0 | — |
| остальные 14 | — | не capital | — | 0 | 0 | — |

Сутки города — 24 тика (`tick_length_city_hours = 1`, `ticks_day = 24`) и **25 реальных часов** (`city_day_real_hours = 25`). После `residual_idle_bps = 500` живой Workshop даёт $3.25 в сутки, спящий — $1.63.

`flagship_store` и `retail_complex` имеют `level_output = 0` не по ошибке: их Capital идёт через конверсию населения, а не через таблицу уровней.

### 1.2 Первая причина: нормировка приклеивает окупаемость к 240 тикам

`content/build.py`, формула в `docs/BALANCE.md` §4:

```
output(a,1) = cost(a,1) × output_weight_bps(a) / 10000 / normalization_payback_ticks
```

`normalization_payback_ticks = 240`. Любое производящее здание **по построению** отбивает свою цену за 240 тиков = 10 суток города, независимо от того, сколько оно стоит. Отсюда следует то, что владелец назвал «по процентам всё равно одинаково»: это не баг, это нормировка. Абсолютный заработок поднимается только вложением, а процент — только модификаторами.

### 1.3 Вторая причина: фонд умеет только резать

`packages/engine/src/economy.ts:571`:

```ts
const paidPool = budget < total ? budget : total
```

Пул выплаты тика = `min(дневной бюджет тика, Σзапросов)`. Верхняя половина этого `min` — потолок: **сколько бы ни было в фонде, выплатить больше суммы запросов нельзя.** Рядом, строка 558:

```ts
state["payroll_ratio_bps"] = ratio > bps ? bps : ratio
```

Коэффициент зажат сверху `BPS`, то есть 100%. Фонд физически не может заплатить больше запроса.

Что из этого следует численно: при обороте $5 млн в сутки выплата игрока не меняется ни на цент относительно оборота $50 тыс. Разница копится в фонде и на 30-е сутки уходит в `reserve_cork` через `fundCap` (`economy.ts:951`). Замер дал $206 тыс. невыплаченных на 30-е сутки.

Питоновский двойник — `content/tick.py:1196-1197`, те же две строки.

## 2. Целевая модель

Четыре утверждения, которые должны стать верны после E1–E6.

**Заработок не фиксирован.** Ни одна задача не вписывает «игрок получает $8.69». Все числа в этом ТЗ — точки насыщения: столько выплатится, **если** фонд наполнен до соответствующего уровня. Оборота нет — фонда нет — выплата падает автоматически. В HUD показывается факт тика, не обещание.

**Фонд связан с зарплатой в обе стороны.** Сегодня фонд умеет только резать выплату вниз. После E1 он умеет и поднимать её вверх, до потолка-параметра. Потолок повышает крышу, а не пол.

**Стратегия обгоняет капитал.** После E3 и E4 отношение из §1.7 обязано стать больше единицы. Целевая проверка: глубокий город даёт **больший процент**, чем минималист, а не только больший абсолют.

**Касса не печатает.** Ни в одном месте ТЗ не появляется прибавления Capital без `mintFromBacking`. Всё, что делает E1, — разрешает потратить уже сминченное, лежащее в фонде.

### 2.1 Что именно считает потолок

После E1 пул выплаты тика:

```
pool = min( Σзапросов × boost / BPS,  tick_budget,  fund )
```

Три ограничителя, и все три обязаны остаться:

- `Σзапросов × boost / BPS` — потолок щедрости. Параметр пака.
- `tick_budget` — предохранитель кассы. Держит I4 и не даёт выпить фонд за день.
- `fund` — физика. Нельзя отдать то, чего нет.

Точка насыщения выводится из второго ограничителя. `tick_budget = fund / payroll_daily_divisor / ticks_day`. Чтобы буст применился целиком, нужно:

```
fund ≥ payroll_daily_divisor × Σзапросов_за_сутки × boost / BPS
```

При 200 играющих с одним Workshop (`Σзапросов_за_сутки ≈ $684`) и `boost = 30000` фонд должен держать **$28 728**. Меньше фонд — меньше выплата, и это правильно.

### 2.2 Почему ×3, а не ×8 постоянно

Симуляция 30 суток на 200 игроках, оборот падает по типичной кривой после запуска:

| потолок | выплата держится | что происходит дальше |
|---|---|---|
| ×3 | все 30 суток | переживает полный обвал оборота |
| ×5 | 13 суток | ломается на 14-е |
| ×8 | 9 суток | ломается на 10-е |

Отсюда `R-E-02`: ×8 только на стартовое окно, дальше ×3. Окно объявляется честно, с датой окончания в HUD.

### 3.2 Правка `fixDayBudget`

TypeScript — `packages/engine/src/economy.ts:310-327`. Сейчас:

```ts
  state["day_budget_day"] = day
  const div = asBig(cfg["payroll_daily_divisor"])
  state["day_budget"] = div === 0n ? 0n : asBig(state["fund"]) / div
```

Становится: дневной бюджет = **бо́льшее** из «горизонт фонда» и «сглаженный приток».

```ts
  state["day_budget_day"] = day
  const div = asBig(cfg["payroll_daily_divisor"])
  const horizon = div === 0n ? 0n : asBig(state["fund"]) / div
  const inflow = smoothedInflow(cfg, state)
  state["day_budget"] = horizon > inflow ? horizon : inflow
```

`smoothedInflow` — новая функция в том же файле, **не экспортируемая**:

```ts
function smoothedInflow(cfg: Dict, state: Dict): bigint {
  const buf = asList(state["fund_in_day_buf"])
  let sum = 0n
  let n = 0n
  for (const x of buf) {
    sum += asBig(x)
    n += 1n
  }
  if (n === 0n) return 0n
  return sum / n
}
```

Зачем это нужно. Без притока стартовый день выглядит так: в фонд упало $10 000 хайпа, `day_budget = 10000/14 = $714`, буст упирается в бюджет и даёт игроку $3.57 вместо $3.42. Вау-эффекта нет. С притоком `day_budget = max(714, 10000) = $10 000`, буст становится рабочим ограничителем, выплата поднимается до `Σзапросов × 3`.

Наполнение буфера. В том же `fixDayBudget`, в ветке `if (hour === 0n && tick_index !== 0n)`, рядом с уже существующим `payroll_day_buf`:

```ts
    const inBuf = asList(state["fund_in_day_buf"])
    inBuf.push(asBig(state["day_fund_in"]))
    state["day_fund_in"] = 0n
    const keepIn = Number(asBig(cfg["payroll_inflow_window_city_days"]))
    if (keepIn > 0 && inBuf.length > keepIn) inBuf.splice(0, inBuf.length - keepIn)
    state["fund_in_day_buf"] = inBuf
```

`state["day_fund_in"]` — новый аккумулятор: сколько Capital пришло в фонд за текущие сутки города. Прибавлять его надо **везде, где растёт `state["fund"]`**. Найди все такие места командой:

```

```

На 2026-09-20 это `mintFromBacking` с `dest=fund`, `applySpend` (возврат 60% траты), `creditCreatorTax`, `corkReturn`, `reserveDrip`. Проверь список сам командой, не по этому абзацу: если появилось шестое место и ты его пропустишь, приток занизится и стартовое окно не сработает.

Оба новых поля — `day_fund_in` и `fund_in_day_buf` — надо завести в genesis: `packages/engine/src/state.ts` рядом со строкой 163, где уже лежит `payroll_day_buf: []`. Значения: `day_fund_in: 0n`, `fund_in_day_buf: []`.

Двойник: `content/tick.py:1114-1132` для `fixDayBudget`, и создание состояния около `content/tick.py:2005`, где уже стоит `"payroll_day_buf": []`.

Комментарий-docstring у питоновской функции гласит `"""Budget is frozen at day start. Intra-day order must not move payroll_ratio."""`. Это инвариант, а не описание. Сглаженный приток тоже замораживается на начало суток — **не** пересчитывай его внутри дня, иначе порядок городов внутри тика начнёт двигать выплату и детерминизм посыплется.

### 3.3 Правка `pay`

TypeScript — `packages/engine/src/economy.ts:545-644`.

Шаг 1. Считаем буст. Новая не экспортируемая функция в том же файле:

```ts
function payrollBoostBps(cfg: Dict, state: Dict): bigint {
  const days = asBig(cfg["payroll_boost_launch_city_days"])
  const winTicks = days * asBig(cfg["ticks_day"])
  if (winTicks > 0n && asBig(state["tick_index"]) < winTicks) {
    return asBig(cfg["payroll_boost_launch_bps"])
  }
  return asBig(cfg["payroll_boost_bps"])
}
```

**Окно считается по `tick_index`, а не по `state["day"]`, и это принципиально.** `state["day"]` — не индекс от genesis: `cityClock` (`state.ts:35-45`) выводит его как `anchor_day + dayOffset`, где `anchor_day_index = 1`. Вдобавок первые сутки короткие: `anchor_hour = 12`, поэтому на день 1 приходится 12 тиков, а не 24. Сравнение `day < 7` дало бы шесть с половиной суток вместо семи. `tick_index < days × ticks_day` даёт ровно 168 тиков окна и не зависит от якоря.

Шаг 2. Строка 571. Было:

```ts
  const paidPool = budget < total ? budget : total
```

Стало:

```ts
  const boost = payrollBoostBps(cfg, state)
  let paidPool = (total * boost) / bps
  if (paidPool > budget) paidPool = budget
  const fundNow = asBig(state["fund"])
  if (paidPool > fundNow) paidPool = fundNow
```

Порядок обрезок не переставлять: сначала буст, потом бюджет, потом фонд. Перестановка меняет остаток целочисленного деления и хеш записи.

Шаг 3. Строки 557-558. Было:

```ts
  const ratio = total === 0n ? bps : (budget * bps) / total
  state["payroll_ratio_bps"] = ratio > bps ? bps : ratio
```

Стало — коэффициент публикуется от фактического пула, а не от бюджета, и зажат сверху потолком буста, а не `BPS`:

```ts
  const ratio = total === 0n ? bps : (paidPool * bps) / total
  const ceil = asBig(cfg["payroll_boost_launch_bps"])
  state["payroll_ratio_bps"] = ratio > ceil ? ceil : ratio
```

**Это перестановка порядка:** `paidPool` считается на строке 571, а `ratio` — на 557. Подними вычисление `paidPool` выше, до присвоения `ratio`. Убедись, что `budget` к этому моменту уже прошёл обнуление на строке 559 (`if (budget > 0n && fund <= 0n) budget = 0n`) — перенеси и его тоже, сохранив относительный порядок.

Шаг 4. Страж `I4_OVER_BUDGET`, строки 640-642, **не трогать**:

```ts
  if (paidSum > budget) {
    throw new TickError("I4_OVER_BUDGET", ...)
  }
```

Он остаётся рабочим именно потому, что `paidPool` обрезан бюджетом на шаге 2. Если после твоей правки этот страж начал срабатывать — ты убрал обрезку бюджетом, вернись к шагу 2. Не «чини» страж.

Шаг 5. Двойник — `content/tick.py:1187-1210`, функция `_pay`. Те же пять правок, тот же порядок, то же целочисленное деление (`//`, не `/`).

## 4. E2 — стартовое окно

### 4.1 Что видит игрок

Контракт дописать в `docs/API.md` одним-двумя предложениями. Экранный контракт — в `docs/SCREENS.md`.

### 4.3 Реальное время окна

`city_day_real_hours = 25`. Семь суток города — это **7 суток и 7 часов реального времени**, а не неделя. Если владелец объявляет окно публично, в анонсе должна стоять реальная дата окончания, а не «7 дней». Посчитай её от момента genesis и положи в отчёт.

### 4.4 Известное ограничение, которое надо назвать вслух

`fixDayBudget` пересчитывает бюджет только в час 0 суток города (`economy.ts:311`, и это защищено инвариантом заморозки из §3.2). Значит деньги, пришедшие в фонд в первые сутки, становятся выплачиваемыми **на вторые сутки города**, то есть до 25 реальных часов спустя.

Это не баг и не чинится в E2: заморозка бюджета внутри суток держит детерминизм. Но это значит, что «вау на первом дне» приходит не в первый час, а в первую городскую полночь. Владельца надо предупредить в отчёте. Если он захочет мгновенную реакцию — это отдельное решение и отдельная задача, потому что оно ломает инвариант заморозки.

`l391_launch_window_published`. Проверяет, что окно не может тихо исчезнуть из провода: если `payroll_boost_launch_bps > payroll_boost_bps`, то в контракте снимка обязаны присутствовать оба поля из §4.2. Правило читает описание API из пака, не из прозы.

## 5. E3 — снятие клипа `output_bps`

### 5.1 Что меняется

`content/params/modifiers.json`, `cap_anchors.output_bps`. Ключ `max_from` перестаёт указывать на `output_growth_bps`.

Новый потолок обязан **выводиться**, а не быть вписанным числом: правило «пак — единственный источник чисел» никуда не делось, и `18000 → 35800` руками — это тот же дефект под другим номером. Потолок = произведение собираемого контента, посчитанное генератором.

## 6. E4 — маяки и синергии влияют на выработку

**Закрыта 2026-09-21, пак 181.** Владелец выбрал вариант 1: `building_link_quantum_mult = 2`. 14 `output_link` в `buildings.json`, величины запечены в `generated.buildings.output_links`, collect не умножает. Страж L393.

Самая содержательная задача по дизайну и самая опасная по балансу. Читай §1.5 до начала.

### 6.1 Что требуется

Каждое из 14 не-производящих зданий должно как-то влиять на **размер** выработки, а не только на расписание и себестоимость. Цель — чтобы город с двумя capital-зданиями и хорошими связками обгонял город с четырьмя capital-зданиями без связок.

### 6.2 Чего делать нельзя

- **Не добавлять новых архетипов.** 18 зданий, 18 GLB, состав закрыт.
- **Не превращать всё в плоский `+X% output`.** Если каждое здание даёт просто прибавку к `output_bps`, то выигрывает тот, кто построил всё, и наклон за стратегию снова становится наклоном за капитал. Нужны **условные** эффекты: связка, а не сумма.
- **Не выдавать Capital за факт постройки.** `DESIGN.md` §2.8. Платит только работающая связка: здание плюс агент плюс ресурсы плюс валидный тик.
- **Не превышать новый потолок из E3.** Если сумма новых эффектов вылезает за `output_bps_reachable_max_bps`, потолок надо пересчитать в генераторе, а не обойти.

### 6.3 Форма, в которой это делается

Через уже существующую грамматику модификаторов, не через новый механизм. Эффект здания описывается как строка модификатора с ключом `output_bps` и **условием применения**. Посмотри, как уже устроены `progression_nodes` (`scope_kind`, `district`, `exclusive_with`) и `modifier_keys.json` (`stacking`, `stage`, `scope`) — новое должно лечь в ту же форму.

**Это единственная задача ТЗ, где требуется дизайнерское решение, а не механическая правка.** Прежде чем писать код: собери предложение — какое здание какой условный эффект даёт, с числами, — и **вынеси его владельцу**. Не выбирай сам. В предложении обязательно покажи пересчитанный наклон §1.7 для трёх городов: минималист, широкий без связок, узкий со связками. Средний обязан проиграть третьему.

### 6.4 Что проверить перед выносом предложения

- `slots.ts` `collectSlotRequests` — куда физически встраивается новая строка модификатора и на какой стадии (`base` или `post`).
- `content/slots.py` — двойник обязан принять ту же форму.
- Порядок применения не меняется: `district_efficiency` уже сидит в output, второй раз не умножаем (`DESIGN.md` §2.9).
- `fragment_rate_bps` считается от gross output **до** `payroll_ratio`. Если ты поднимаешь output, ты поднимаешь и начисление фрагментов. Это ожидаемо, но должно быть названо: пул фрагментов конечен, и `docs/PRIZES.md` придётся пересчитать.

### 6.5 Новое правило линтера L393

`l393_beacons_move_output`. Проверяет, что число архетипов, эмитящих `output_bps`, **больше** числа производящих Capital. Иначе `R-E-04` не исполнено, что бы ни было написано в документации.

## 8. E6 — дефект двойного учёта в `robotics_lab`

Самая маленькая задача. Делать **первой**: она чинит дефект, и её результат входит в базу для замеров E3 и E5.

### 8.1 Решение: снять запекание из пака, оставить рантайм

Штраф `affinity_neighbour_bps` учитывается один раз — в рантайме, где он и есть общее правило «автономный слот работает как неродной работник». Пак перестаёт запекать его в вес.

`content/build.py:1114-1121`, функция `output_weight_bps(data, bid)`. Сейчас у `robotics_lab` вес не хранится в `buildings.json`, и функция подставляет его особой веткой:

```python
    if bid == "robotics_lab":
        return data["economy"]["params"]["affinity_neighbour_bps"]["v"]
```

Ветка удаляется. `robotics_lab` получает обычный хранимый `output_weight_bps` в `content/params/buildings.json`, равный `BPS`, как у остальных производителей. Особый случай в генераторе не остаётся ни в каком виде.

Рантайм `packages/engine/src/slots.ts:675` и двойник `content/slots.py:668` — **не трогать**. Там правило и остаётся.

Почему так, а не наоборот: правило `output(a,1) × normalization_payback_ticks == cost(a,1)` (L31) должно быть одинаковым для всех производителей. Сейчас `robotics_lab` — единственное исключение из нормировки, и это исключение существует только чтобы компенсировать рантайм. Убираем исключение.

### 8.2 Что сломается и что с этим делать

Четыре существующих стража утверждают, что запекание есть. Они не «падают неправильно» — они держали старое поведение, и их надо переписать под новое:

## 11. Пропускная способность выхода — смежное ограничение

Не задача этого ТЗ, но исполнители обязаны про это знать, иначе E1 выпустит деньги, которые некуда вывести.

Дневной лимит вывода — **5% живой глубины пула, глобально на всех игроков** (`bank_daily_limit_pool_share_bps = 500`, потолок `bank_daily_limit_pool_share_cap_bps = 500` в `meta.json`). Личный лимит города — доля от этого глобального по уровню банка: `personalCapWei = globalCap × shareBps / BPS` (`packages/engine/src/bank.ts:29-31`).

Глубина пула на градуации — `pool_depth_quote_wei = 4.2 ETH`. При `eth_usd_8dec = 250087000000` это **$10 504**, значит глобальный лимит всей игры на старте — **$525 в сутки** (`generated.launch.bank_daily_limit_wei = 0.21 ETH`).

Лестница долей банка: L1 2500 bps, L2 4375, L3 5782, L4 6836. Фокус менеджера на `work_finance` добавляет 500 bps.

| глубина пула | глобально в сутки | L1 | L2 | L3 | L4 |
|---|---|---|---|---|---|
| 4.2 ETH ($10 504) | $525 | $131 | $230 | $304 | $359 |
| 16 ETH ($40 014) | $2 001 | $500 | $875 | $1 157 | $1 368 |
| 50 ETH ($125 044) | $6 252 | $1 563 | $2 735 | $3 615 | $4 274 |
| 100 ETH ($250 087) | $12 504 | $3 126 | $5 471 | $7 230 | $8 548 |

Что из этого следует для E1: 200 игроков по $8.69 в сутки хотят вынести **$1 738 в сутки**, для чего нужна глубина **13.9 ETH**. На стартовых 4.2 ETH это не проходит — банк начнёт резать `splitBankLimit` пропорционально (`economy.ts:690`).

Смягчающее обстоятельство: **депозиты игроков сами наращивают пул.** Каждая покупка $CORP кладёт ETH в пул. 200 игроков по $150 входа — это ~12 ETH покупок, пул растёт с 4.2 до ~16 ETH, и лимит становится $2 001 в сутки. То есть механизм само-настраивается, но только если игроки действительно заходят.

Не «чинить» это внутри E1. Если на прогоне обнаружишь, что лимит душит выплату, — назови это владельцу числом, вместе с требуемой глубиной пула.
